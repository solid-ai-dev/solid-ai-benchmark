## 13. Round 5: how the rules are delivered

Registered on 2026-10-26, before any round-5 trial ran and before the
harness could build its arms. It decides ADR-058 in solid-ai-templates and
whether ADR-052 is reopened (solid-ai-dev/solid-ai-templates#2379).

### 13.1 The question and what varies

Which way of delivering the templates gives an agent the best code, and the
same code from one trial to the next?

One factor varies inside a block, the arm. Round 5 runs one setting, block A,
fifteen times:

| Block | Specification | Model | Trials |
| --- | --- | --- | --- |
| A, main | `SPEC.md` | `claude-sonnet-5`, effort `high` | 5 arms × K = 15 |

`SPEC.md` is registered at sha256
`48ee93ff968ef4a3175408c349afd6ce7223d0f3bd25b49ad4521f0fc307e55e`. The harness
refuses a trial whose spec has other content, and the report refuses a round
with a trial that built from one.

Blocks B (`SPEC-thin.md`) and C (`claude-haiku-4-5-20251001`) are deferred to a
later round, sized from block A's measured noise. On the noise round 4 measured
in those settings, they read a chance "worse" in 57 to 69 % of rounds at K = 3,
and no K up to 20 lets them confirm block A.

Held in every trial: the build task alone; the $100 cap and two-hour bound per trial of
[ch. 6.1](../architecture/06-runtime-view.md); the scoring of [ch.
8.6](../architecture/08-crosscutting-concepts.md); `gpt-6-astra` through `codex exec` at
effort `high` as the only judge, three times per trial, with no cross-check. The budget
is not a factor: every block records each trial's cost, which shows what a shorter file
saves without a cap that ends trials early.

The order and the count are fixed:

- Block 1 runs `none, inline, hybrid, reference, skills`, and each block after it
  starts one arm later. Over 15 blocks each arm runs three times in each place, so a
  drift within a block lands on no arm in particular.
- K is 15 and allows no escalation. No verdict is read before block 15 is in.

### 13.2 The arms

Every arm draws on the same templates: solid-ai-templates at `9086e0ff`,
resolved for the roots `backend-api`, `backend-auth`, `backend-database`,
`frontend-ux`, `base-security` and `base-data-governance`, the union in
resolution order. Every generated file is made once for the round, before
block A, and committed with the record of how it was made.

| Arm | What the agent gets | How it is made |
| --- | --- | --- |
| `none` | Nothing | — |
| `reference` | A file naming each template of the chain, to read before starting, with the templates vendored as `hybrid`'s are | Fixed text, written once |
| `inline` | Every adopted rule, copied in | One non-interactive generation following `templates/core/agents.md`, inline model |
| `hybrid` | The silent, unenforced rules copied in; the rest referenced, with the templates vendored | The same generation, hybrid model |
| `skills` | A root file of facts and every-turn rules, a trigger table, and one skill per kind of task | `resolve_chain.py --emit` with the skills mirrored into `.claude/skills`; the facts filled from the brief |

`skills` is emitted with a declined list, as a project's adoption gives
one: the sections the brief rules out for tariff, fixed once from the
brief alone and kept in `harness.ROUND5_DECLINED`. Only a section that
cannot apply is declined:

| Template | Declined section | Why, from the brief |
| --- | --- | --- |
| `security/security.md` | Server-Side Request Forgery (SSRF) | Nothing reaches the network |
| `security/security.md` | File uploads | It names exports, and no upload |
| `security/security.md` | CORS | One administrator in one browser: no cross-origin client |
| `backend/auth.md` | API keys (service-to-service) | No other service |

`inline` and `hybrid` are generated by `claude-sonnet-5` from the chain, `agents.md` and
the brief of [ch. 5.5.4](../architecture/05-building-block-view.md), with no interview:
every rule that applies to the brief's project is adopted. The record keeps each file's
line and word count, and the report prints them.

### 13.3 Hypotheses

A row is held against [ch. 8.1.2](../architecture/08-crosscutting-concepts.md)'s
margins, but for adherence, which is held within 8 pp: one checklist item of 13. A
pair's adherence differs by about one item from build to build, so no affordable K
rules out a loss of less than one.

**H1, ADR-058.** A root file with task skills delivers what hybrid delivers.

| | |
| --- | --- |
| Contrast | `skills` minus `hybrid`, paired within the block |
| Primary rows | adherence, the security and data-protection probe pass rates, and the judge's security and data-protection rows |
| Supported | every primary row is held or better |
| Refuted | any primary row is worse |
| Otherwise | inconclusive; round 5 allows no escalation |

**H2, consistency.** Built by a tool, the root file makes an arm's trials
agree with each other more than a generated hybrid file does.

| | |
| --- | --- |
| Measure | conventions agreement per arm: for each pair of the arm's trials, the share of the adherence items both measured on which the two agree, meaned over the pairs |
| Supported | `skills` agrees at least as much as `hybrid` |
| Refuted | `skills` agrees less than `hybrid` by 0.15 or more |

A mean over pairs keeps its expected value as trials are added. Round 4's
measure, the share of items on which every trial agrees, falls with each trial,
so its bar would mean something else at K = 15. With one agreement value per arm
there is no interval; the result is descriptive.

**H3, ADR-052.** A file that only names the templates delivers less than
hybrid.

| | |
| --- | --- |
| Contrast | `reference` minus `hybrid`, paired within the block |
| Primary rows | as H1 |
| Supported | any primary row is worse |
| Refuted | every primary row is held or better; ADR-052 is then reopened |

**Secondary, no verdict:** every metric of [ch.
8.6](../architecture/08-crosscutting-concepts.md) for every arm against `none`; `skills`
against `inline`; each arm's worst trial beside its mean; structure and security
agreement as [round 4's registration, 12.1](round-4.md) defines them; cost, turns,
tokens and wall time; and the words each arm puts in context on every turn.

### 13.5 How K was sized

Sized on 2026-10-27 (#38), before any round-5 trial, from the per-trial values of
round 3, block A's setting. Per pair, adherence differed by 8 pp and the judge's
security row by 0.41 points; the probes and the judge's data-protection row sat at
the top score. The report's own rules ran 600 times per cell on that noise, so
each share is good to about two points:

| K | Skills equal hybrid: H1 supported | No real difference, yet a row reads worse | A loss the size of the margin passes as held | A real loss is caught |
| --- | --- | --- | --- | --- |
| 3 | 29 % | 36 % | 46 % | 77 % |
| 5 | 26 % | 21 % | 30 % | 71 % |
| 10 | 55 % | 14 % | 7 % | 92 % |
| 15 | 73 % | 12 % | 4 % | 98 % |
| 20 | 87 % | 8 % | 5 % | 100 % |

At K = 15 a margin-sized loss passing as held, and a real loss going unseen, stop
getting rarer. Fifteen is also a multiple of five, so the rotated order puts every
arm in every place equally often. In round 4, most of the judge's noise came
from build to build rather than from re-reading one app, so more blocks, not more
readings, buy the precision.

Nothing in this section changes once a round-5 trial has run.

### 13.6 Code size

Amended on 2026-10-28 (#39), before any round-5 trial. Round 5 reads size as app
code and test code, against a band, in place of source lines and files:

| Row | What it counts | Direction | Margin | Smallest change that matters |
| --- | --- | --- | --- | --- |
| App code, lines | The app's Python outside its tests, with its templates, styles and scripts | down | 20 % relative | 40 % |
| App code, files | The same files | down | 20 % relative | 40 % |
| Test code, lines | Python under a `tests` directory or named `test_*.py`, `*_test.py` or `conftest.py` | none | — | — |

- An app-code row is **held** where the whole interval sits below the margin,
  even above zero, and **worse** only where it sits wholly past it.
- Docs and configuration count toward no size.
- Committed bytecode, caches, databases and coverage data count as artifacts
  nobody asked for.
- Source lines and files are still printed, without a verdict.

Why: a better solution is often a little bigger, with tests, error handling and
layering, so a small rise should not read as worse. In round 4's trees, tests
were 10 to 40 % of the Python lines, and docs, templates and config outnumbered
the app's modules, so the old rows measured neither code nor bulk cleanly.

### 13.7 The prompt

Amended on 2026-10-29, after a first start of block A. Every arm's prompt gains
one sentence after its first:

> SPEC.md is the approved plan, and nobody will answer questions during this
> run, so build it to the end without stopping for approval.

Why: `templates/core/review.md` at `9086e0ff` asks for a plan, and its
approval, before implementation code, unless the requester specified the change
in full. A trial runs headless, so nobody approves. The first start's
`inline-1` printed a plan, cited that rule, and ended after 2 minutes and $0.30
with nothing built. Without the sentence a
templates arm loses for waiting, not for the code it guides. The sentence goes
to every arm, `none` included, so the context file stays the only difference.

The first start, from 08:21 to 09:47 on 2026-10-29 in `C:/efficacy/r5-main`:

| Trial | What happened |
| --- | --- |
| `none-1` | Voided for a command run outside its workspace, then rerun to completion |
| `inline-1` | Stopped after its plan, as above |
| `hybrid-1` | Stopped mid-build when block A was stopped |

Its four trials count toward nothing. None was scored or judged. Block A
restarts at block 1 in a fresh run root, and the report refuses a build run
whose recorded prompt is not this one.
